# 未來功能實施計畫

## 1. 航班卡片內展開「票價產品/組合」詳情

- **需求描述**:
    - 在 `FlightCard.vue` 組件上，當用戶對某個航班感興趣時（例如，在用戶按艙等初步篩選後），提供一個交互方式（如點擊「查看票價選項」按鈕）。
    - 點擊後，在該航班卡片下方或一個專門的區域/彈窗中，展開展示該航班在用戶選定的大艙等（如經濟艙）下的不同「票價產品/組合」。
    - 每個「票價產品/組合」應清晰列出其特有的：
        - 產品名稱 (例如: "經濟艙 Lite", "標準經濟艙", "彈性經濟艙")
        - 最終價格
        - 詳細行李額度 (件數、重量)
        - 改票規則與費用概述
        - 退票規則與費用概述
        - 座位選擇權限 (免費、付費、不可選)
        - 其他重要服務差異 (如里程累積、餐食等級等，視數據可得性而定)
- **UI/UX 設計考慮**:
    - 參考主流航空公司網站（如國泰航空、長榮航空、中華航空）在選擇航班後展示不同票價等級/組合的界面。
    - 設計應清晰、易於比較不同票價產品間的差異和性價比。
    - 考慮使用卡片式佈局、表格或清晰的分組條目來呈現每個票價產品。
    - 點擊某個票價產品後，用戶應能進入下一步（例如填寫乘客資訊）。
- **相關前端組件**:
    - `FlightCard.vue`: 需要添加觸發機制和容納展開內容的結構。
    - 可能需要新的子組件來渲染單個「票價產品/組合」的卡片。
- **數據需求 (後端支持)**:
    - 後端 API 需要能夠返回特定航班在指定大艙等下，所有可用的「票價產品/組合」及其詳細屬性。
    - 這可能意味著後端需要從數據源獲取或構建這些細化的票價等級資訊。

## 2. 擴展資料庫以支持詳細票價規則

- **需求描述**: 為了支持前端展示詳細的「票價產品/組合」資訊，後端資料庫需要能有效存儲這些結構化的規則。
- **方案一 (首選 - 擴展 `ticket_prices` 表)**:
    - 調整 `ticket_prices` 表的結構，使其能夠代表一個「票價產品/組合」而不是僅僅是一個艙位的基本價格。
    - 為 `ticket_prices` 表添加新欄位，例如：
        - `fare_product_name_zh` (票價產品中文名, e.g., "經濟艙 Lite")
        - `fare_product_name_en` (票價產品英文名, e.g., "Economy Lite")
        - `fare_basis_code` (票價基礎代碼, 可選, 某些 GDS 系統會提供)
        - `baggage_allowance_description_zh` (行李額度中文描述)
        - `baggage_allowance_description_en` (行李額度英文描述)
        - `change_policy_summary_zh` (改票政策摘要中文)
        - `change_policy_summary_en` (改票政策摘要英文)
        - `cancellation_policy_summary_zh` (退票政策摘要中文)
        - `cancellation_policy_summary_en` (退票政策摘要英文)
        - `seat_selection_type` (座位選擇類型, e.g., "free", "paid", "not_available")
        - `price` (該票價產品的最終價格，取代原有的 `economy_price`, `business_price`, `first_price`)
        - `cabin_type` (該票價產品所屬的大艙等，e.g., "Economy", "Business", "First" - 這個欄位可能需要重新加入或以其他方式標識)
        - 其他航空公司特有的服務標識欄位。
    - **注意**: 如果採用此方案，原有的 `economy_price`, `business_price`, `first_price` 欄位將被單一的 `price` 欄位取代，並通過 `cabin_type` 和 `fare_product_name` 來區分。這是一個較大的數據模型變更。
- **方案二 (備選 - 新建 `fare_rules` 或 `cabin_features` 表)**:
    - 創建一個獨立的表來管理標準化的票價規則或艙位特性。
    - `ticket_prices` 表通過外鍵關聯到這些規則。
    - 優點：規則可重用，減少冗餘。
    - 缺點：查詢可能更複雜。
- **實施考量**:
    - 需要仔細規劃資料庫遷移。
    - 後端服務邏輯 (特別是 `PriceAnalysisService` 和 `FlightSearchService`) 需要相應調整以處理新的數據結構。

## 3. 在 `flights` 表中添加 `aircraft_type` 和 `duration_minutes`

- **需求描述**: 增強航班基礎資訊的豐富度。
- **`aircraft_type`**:
    - 類型: `VARCHAR`
    - 描述: 執飛該航班的具體飛機型號 (e.g., "Boeing 777-300ER", "Airbus A321neo")。
    - 用途: 可在航班詳情頁或訂單確認頁展示，供用戶參考。
- **`duration_minutes`**:
    - 類型: `INTEGER`
    - 描述: 航班的總飛行時長，以分鐘為單位。
    - 用途: 允許前端更精確地計算和展示飛行時間（例如 "3小時15分鐘"），而不是依賴起降時間的簡單計算（可能涉及時區問題）。
- **數據需求**:
    - 後端 API 需要從數據源獲取這些資訊並填充到 `flights` 表。
    - TDX API 或其他航班數據提供商可能提供此類資訊。

## 4. 在訂單流程中顯示更詳細的航班資訊

- **需求描述**: 在用戶選擇完具體的「票價產品/組合」並進入後續流程（如填寫乘客資料、確認訂單）時，提供更全面的航班相關資訊。
- **可展示資訊**:
    - 飛機型號 (`aircraft_type` from `flights` table)
    - 精確的飛行時長 (`duration_minutes` from `flights` table)
    - 中轉資訊（如有，包含中轉機場、停留時間）
    - (若有) 預計的餐飲服務級別
- **相關前端組件**:
    - 乘客資訊填寫頁面
    - 訂單確認/預覽頁面
- **目的**: 增強用戶的知情權，提升預訂體驗的透明度和專業度。
